# 新手入门说明

[English](rookie-onboarding.md) · [繁體中文（香港）](rookie-onboarding_HK.md)

这份说明写给第一次用 AI 做软件的人：刚启动项目的产品经理、不写代码的创业者、想把自己的经验做成工具的设计师或分析师，或者只是好奇想试试的你。用 constitution skill 不需要会写代码。不过它写出来的文件里会有一些工程上的词，你也会被请来做几个决定。这一页讲清楚三件事：活儿大概怎么推进，每个文件是干什么的，每一步可以对 AI 说什么。

建议先从头到尾读一遍，大约半小时，之后用到哪一节再回来翻。如果只是想查某个词，可以看[新手词典](rookie-wiki_CN.md)，里面用大白话解释了做应用时常见的词。

如果只记一句话，就记这句：做什么、为什么做，由你决定；怎么做，由 AI 提方案并动手；决定过的事情，记在项目文件里。

## 开始之前

你需要准备三样东西：

- 一个 AI 编程工具：Codex、Cursor 或 Claude Code，有一个就够了。
- 在这个工具里装好技能。[README 里的“快速开始”](../../README_CN.md#快速开始)只要发一段话就能装好。
- 一个项目文件夹，也就是你电脑上专门放这个项目的普通文件夹。空的也没关系。

你不需要懂编程语言，不需要背下这份说明里的文件名，也不需要自己挑模板。这些交给 AI，它会告诉你它选了什么。

## 一、一个项目大概怎么走

### 用 Standard 做新想法的第一周

假设你想做一个帮小团队收集客户意见的工具。用 Standard 的话，过程大致是这样：

1. 你用平常说话的方式讲你的想法，包括还没想明白的部分。
2. AI 问几个会影响计划的问题：给谁用、第一版必须做到什么、什么可以往后放、什么绝对不能出错。你已经回答过的，它不会再问。
3. 你能答的就答。答不上来的，AI 会提一个稳妥的默认选择，并记成“假设”，以后可以再改。
4. AI 把计划写进项目里的文件。
5. 你把计划读一遍，哪里不对就指出来。这一步省下的返工最多。
6. AI 提出第一个小任务，结果要清楚，也要有检查办法。
7. 你说“开始”。AI 动手做，跑完检查，再用大白话告诉你改了什么、怎么试用。
8. 想的话，可以请第二个 AI 工具或者工程师审查一遍改动。
9. 新的决定写回文件，然后进入下一个任务。

整个过程里你都不用读代码。你读的是计划、结果和简短的汇报。

### 谁负责什么

通常有四个角色，一个人或一个工具可以身兼几个。

你是负责人。目标、优先级，以及那些改起来代价很大的事，都由你来定。有风险的改动要你批准，最后接不接受也由你说了算。

实现者（implementer）是一个 AI 工具，在约定好的任务范围内改文件、跑检查。

审查者（reviewer）是另一个 AI 工具或一位工程师，对照任务和项目规则检查改动。

项目文件是大家共享的记忆。下一个对话、下一个工具或下一个人，都不用依赖某次旧聊天里说过的话。

Codex、Cursor 和 Claude Code 都可以当实现者，也都可以当审查者。按你手上有的工具和具体的活儿来安排，没有固定的分工。有一个习惯很有用：每次改动只安排一个主要修改者，免得两个工具同时改同一块地方。

### 为什么要写下来

AI 对一次聊天的记忆很短，也带不到新的聊天里。写进项目的文件却一直在。计划放在文件里，你就可以开新对话、换工具、休息一周，或者把项目交给别人，工作都能从写下来的内容接着做，不用靠谁的记性。

## 二、你的任务需要多少结构？

这个技能有几种工作方式。你不需要叫出名字，描述清楚任务，AI 会自己选。不过了解一下每种方式长什么样，心里会更踏实。

### 直接做：已经说清楚的小任务

任务很小、要求也清楚，AI 就应该直接做，再跑相应的检查。不用问答，也不建新文件。

例子：改一个错别字；改一下按钮上的文字；回答一个关于你代码的具体问题；把你贴进来的一份备忘录缩短。

### Flash：轻量，适合各种工作

Flash 适合需要先理一理、但用不着整套项目流程的任务。日常工作、调研、写文档、做软件，以及做可以反复用的能力（比如技能），都可以用它。

例子：比较三款收集意见的工具并推荐一款；做一个技能，把会议记录整理成同事们都能复用的行动清单；写一个小脚本，读取用量导出文件，算出还剩多少额度；给采购团队准备一份简短的决策幻灯片；把一个团队会议挪到新时间，并通知参会的人。

### Standard：完整的软件项目

Standard 适合要做出真正软件的情况：它会不断发展，会有真实用户，或者有好几个人、好几个 AI 工具一起参与。它会写出整套项目文档，然后通过一个个经过检查的小任务往前推进。

例子：给小团队用的意见收集箱、公司内部的审批系统、预约服务、AI 客服助手。

### Retrofit：已有代码，但没有文档

如果你已经有一套没人写过文档的代码，Retrofit（补建）会一部分一部分地补文档，从你马上要改的那块开始。它不会一上来就想把所有东西都写清楚：当初的想法已经没人记得，从头硬写一份大文档，大部分内容只会是猜测。

### 拿不准选哪个？

问自己几个问题：

- 要做什么、怎么检查，是不是已经很清楚？那就直接提要求。
- 这是不是一件单独的工作，比如一次比较、一份文档、一个脚本、一个技能或一个操作，只是需要先把目标和终点说定？那就用 Flash。
- 这是不是一个会持续做下去的产品，有用户、有数据、有好几个部分？那就用 Standard。
- 是不是已经有很多代码了？那就用 Retrofit。

实在判断不了，就直接说：“我不确定这件事需要多少规划。请推荐一种模式，用一两句话说明理由。”从轻的开始也完全可以。等事情多到不好掌握、好几个部分或好几个人要依赖稳定的约定，或者交接需要单独的记录时，Flash 的工作可以再换成更完整的结构。

## 三、Flash 一步一步来

### 任务约定

Flash 一开始，会先把任务说定，形成一份简短的约定，文档里叫 task contract。它包括七项内容。下面用一个例子贯穿：给产品团队比较三种收集客户意见的方法。

1. 目标：想要什么结果，为什么。“选出一种下个月就能开始用的收集方法。”
2. 使用者或读者：谁会用这个结果，或者谁来评判它。“我们的产品团队，大家都不是工程师。”
3. 背景：现在的情况，以及要参考的材料。“我上个季度的笔记，还有我们已经试过的两款工具。”
4. 范围：包括什么，以及特意不做什么。“比较三个方案。不要注册任何账号，也不要联系供应商。”
5. 限制：会影响结果的条件。“要在我们现在的预算之内，还要能接入我们正在用的聊天工具。”
6. 可观察的完成标准：做完时会是什么样子，怎么检查。“一页纸的比较和推荐，每个重要说法都标明来源。”
7. 未知项：还没定的问题和暂时的假设。“我们不知道其中一家现在的价格，标出来，不要猜。”

小任务可能两三句话就把这七项都说完了。持续好几天，或者要交给别人接手的工作，就需要把它们写下来。

### 结果不能随便动，计划可以改

约定说的是“怎样算成功”。计划说的是 AI 打算怎么做到：用什么办法、分哪几步、现在做到哪儿。某个办法行不通，或者有了更好的信息，计划就应该改。可结果不能跟着悄悄变：AI 不应该降低标准、换掉读者，或者为了迁就自己做出来的东西而改动交付内容。如果结果确实需要改，那要和你商量，并且把改动写下来。

还有一点：初稿、进度汇报，或者一个已经启动的任务，都不等于完成。如果有东西还在运行或者卡住了，AI 应该直接说清楚。

### 四种额外细节

在约定之外，AI 只补充任务真正需要的细节。一共有四种，一个任务可能用到好几种，也可能一种都不用。

行为，用在会反复运行的东西上：脚本、软件功能、技能、智能体。值得写清楚的是：输入什么、怎么启动、输出什么、两次运行之间要保留什么、几个例子（包括刁钻的情况），以及输入缺失或出错时怎么办。拿那个额度报告脚本来说，就是要问：导出文件是空的怎么办？额度那一项缺了怎么办？

证据与判断，用在调研、比较、诊断和给建议上。值得写清楚的是：必须回答哪些问题、证据从哪里来（要带日期，因为信息会过时）、按什么标准比较各个选项、结论有几成把握。好的调研会把“看到的事实”和“推出来的判断”分开。

内容与结构，用在文档、幻灯片、消息这类给人看的东西上。值得写清楚的是：写给谁、最想说的是什么、提纲，以及呈现方式，也就是格式、语气和篇幅。像幻灯片这种讲究版面的东西，检查时要看实际渲染出来的效果，光看文字不够。

行动，用在真的要改动某样东西的时候：整理文件、改会议时间、更新一条记录、发送一份报告。值得写清楚的是：具体改的是哪一个、现在什么样、改完应该什么样、事先必须满足什么条件、步骤顺序，以及怎么确认结果。操作发出去，不代表已经成功。AI 应该去看实际结果，比如日历上那个会议的新时间。

这些不用你来挑。它们不是几种不同的模式，也不需要各建一个文件。比如一次市场比较最后要做成幻灯片，就同时用到证据和内容两种；一个每周出报告的智能体，可能四种都会用到。

### Flash 把东西放在哪里

一次性的任务，在聊天里说清楚通常就够了。持续进行的工作，可以用一套很轻的结构：

- `AGENTS.md` 放稳定的项目背景：这是什么项目、重要文件在哪里、一直沿用的约定，以及怎么检查工作。
- `docs/PLAN.md`（或者已有的任务简报）放任务约定、额外的细节、当前的计划，以及已经检查过什么的证据。

这只是一个起点，不是必须建的文件。如果一个技能已经在自己的 `SKILL.md` 里写清楚了行为，或者项目里已经有任务记录、数据格式定义，AI 应该直接引用它们，不要再复制一份。需要的话，可以用 [AGENTS.md](../assets/flash-templates/AGENTS.md) 和 [PLAN.md](../assets/flash-templates/PLAN.md) 这两个可选模板起步。

### 怎么检查 Flash 的结果

不同的结果，检查方式也不一样：

- 会运行的东西：拿有代表性的例子实际跑一跑，看输出。用假数据或演练（dry run）得到的结果，要标明是这样得到的。
- 调研：把重要的说法和来源、日期对一对，确认缺口和互相矛盾的地方都摆在明面上。
- 文档或幻灯片：读成品；讲究版面的，要看渲染出来的样子。
- 操作：看操作之后的实际状态，或者系统返回的回执和状态。

任何 Flash 任务结束时，都可以问这一句：“我们约定的内容里，哪些完成了？你怎么知道的？还有什么没做完？”

### 可以直接复制的 Flash 提示词

把尖括号里的内容换掉：

```text
请用 constitution-skill 的 Flash 模式处理这个任务：<描述任务>。
结果是给 <谁> 用的。背景情况是：<笔记或文件>。
先写一份简短的任务约定：目标、读者、范围和不做的事、限制条件、怎样算完成、还没定的问题。
只补充这个任务需要的细节，并把计划和要达到的结果分开写。
先在这个对话里整理；如果建一个项目文件方便以后复用，再建。
```

想了解更多，可以看 [Flash 指南](flash-mode.md)、[组件说明](flash-components.md)和[场景示例](flash-scenarios.md)（都是英文）。

## 四、Standard 一步一步来

### 规划时的对话

Standard 从提问开始。问题通常围绕这些方面：用户是谁、要解决什么问题、第一版必须做到什么、什么可以往后放、什么绝对不能出错，以及预算、期限、隐私、必须配合的现有系统这类限制。问题没有最低数量。AI 只该问会影响计划的问题，你已经说过的，它应该直接用。

几个小建议：

- “我不知道”是个好回答。AI 应该给出一个合理的默认选择，用大白话解释，并标成假设。
- 用你自己的话讲问题。“我们团队的客户意见都散落在一个共享表格里，经常找不到”，比“我想要一个 React 应用”有用得多。
- 说说你要替代的是什么（一张表格、一份问卷、一套手工流程），以及哪些东西你最不想丢。
- 如果问题里有你不懂的词，先问清楚这个词再回答。还可以追问一句：“我的回答不同，会改变什么？”

### 你会拿到哪些文件

Standard 会写出一小套文档，一般放在 `docs/` 文件夹里，另外在项目最外层放一个 `AGENTS.md`。每份文件回答一个不同的问题。

`SPEC.md` 回答“这个产品能为用户做什么”。里面写目标、用户、主要流程、特意不做的事（非目标）、限制条件，以及验收标准，也就是一条条可以检查的“怎样算完成”。这里面不写代码。

`ARCH.md` 回答“里面有哪些部分，它们怎么拼在一起”。里面写有哪些模块、各管什么、数据放在哪里、选了什么技术以及理由，还有产品怎么运行。它也会记下产品形态：这个项目属于哪种常见的产品类型，加了哪些能力，用了哪套默认技术。

`RULES.md` 回答“每次改动都要守哪些规矩”。里面是对这个项目真正有用的编码约定、测试要求和安全规则。泛泛的编程建议不放在这里。

`CONTRACTS/` 回答“各部分之间到底约定了什么”。里面写接口的格式、数据库表的结构、事件消息和文件格式，写得很精确，常常用标准格式，还会附上例子。

`DECISIONS/` 放那些很难反悔的决定，比如用哪种数据库。每一条都会写当时的背景、做了什么选择、要付出什么代价，以及被否掉的其他方案。工程师管这种记录叫 ADR（architecture decision record，架构决策记录）。

`TASKS/` 放接下来的一个个小任务。每个任务有一个目标、可以动和不能动的范围、验收标准，以及用来检查的具体命令。任务是一次性的：做完了、经验也记下来了，就可以清理掉。

`AGENTS.md` 是给 AI 工具的说明书：先看哪里、跑哪些命令、哪些地方很敏感、什么需要你批准，以及做完怎么汇报。

打个比方：需求说明（SPEC）像楼盘的宣传册，架构（ARCH）像户型图，规则（RULES）像建筑规范，约定（CONTRACTS）像门框，所有要穿过去的东西都得合尺寸。决策记录是签过字的变更单，任务则是今天的派工单。

除了任务以外，这些文件都要长期保留，项目有变化时要跟着更新。任务、草稿笔记和一次性的计划，用完就可以扔。

### 看看样例项目

技能里带着一个填好的样例，叫 [Feedback Inbox](../assets/examples/feedback-inbox/)。这是一个给 3 到 15 人的小型产品团队用的工具：从公开表单收集客户意见，把意见归成主题，再把最有价值的那些变成开发任务。随手翻翻，看看好的文档长什么样就行，不用每一行都看懂。

有几处值得留意：

- 它的需求说明列出了非目标，比如不替代团队现有的任务管理工具，也不让 AI 直接回复客户。把不做的事写下来，AI 就不容易跑偏。
- 它的验收标准是谁都能检查的，比如“客户可以通过公开表单提交意见，并看到确认页面”。
- 它的第一条决策记录解释了为什么把要发出的事件先存在主数据库里，没有另外加一个消息服务：少运维一个服务，代价是多一点点延迟，能承受的访问量也有上限。被否掉的方案和理由都列出来了。
- 它的[第一个任务](../assets/examples/feedback-inbox/docs/TASKS/001-bootstrap-feedback-inbox.md)写明了可以动哪些文件、不能动哪些文件，以及用哪些命令证明它能用。

### 读计划时的检查清单

技术选得好不好，你不用判断。但你需要确认计划和你的本意一致。可以逐条过一遍：

- 需求说明里描述的用户和问题，和你自己会怎么说一致吗？
- 非目标对不对？有没有你绝不想在第一版里出现、却没列进去的东西？或者列进去了，其实你需要？
- 每条验收标准，你自己能检查吗？或者能看着别人检查吗？
- 这些假设你能接受吗？
- 那些待定问题是真的还没定吗？有没有什么事情依赖它们？
- 第一个任务做完，你能看到或者试用到点什么吗？
- 遇到那些重大、难以反悔的选择，AI 有没有请你批准？有没有用你听得懂的话解释各个选项？

只要有一条的答案是“不”或者“不确定”，就说出来。改计划，比改软件便宜得多。

## 五、文件里常见的十个概念

下面这十个概念会反复出现。每一节都会讲：它是什么，为什么和你有关，你可以做什么。

### 1. 假设和待定问题

假设，是写下来的猜测，让大家都知道这是猜的：“我们假设第一版每套系统只给一个团队用。”待定问题，是还没人做决定的事：“匿名提交的意见，要不要附一个回复链接？”

这两样都很正常。技能会把它们放在专门标出的段落里，不会埋在正文里。你要做的是读一读，确认或纠正这些假设，并留意有没有任务依赖某个待定问题。依赖待定问题的任务，还不能开工。

### 2. Schema 和 migration

Schema 是你的产品存储数据的“形状”。一张 `feedback` 表，有 `id`、`source`、`message`、`created_at` 这几列，就是一个 schema。它很像 Excel 表格的表头，区别在于数据库会强制大家遵守。

Migration（迁移）是一段修改 schema 的脚本，改动会被记录下来，也可以重复执行，比如“给 `feedback` 表加一列 `tags`”。

有两点值得知道。第一，一旦有了真实用户，每次改 schema 都会碰到他们的数据：加一列通常是安全的，改列名、删列，或者改变某一列的含义，往往有风险。第二，大多数团队把 migration 当成只能往前走的：发现某个 migration 有错，就再写一个新的去修，不会回头改旧的。

所以，新增或修改 schema 的决定需要你明确批准。如果已经批准的任务里写清楚了这项改动，AI 可以照着做，不必再问一遍。在正式运行的产品上执行 migration，还需要另外的权限。你永远不用自己写 migration，但要留意它什么时候正在发生，并问一句：“这个能撤回吗？已有的数据会怎样？”

### 3. API 和 contract

API（application programming interface，应用程序接口）是一个软件和另一个软件说话的方式。最常见的是 web API：一个程序往某个网址发出请求（request），另一个程序回一个响应（response），内容常常是一种叫 JSON 的文本格式。可以把它想成餐厅的菜单：上面写着能点什么、会上什么菜；只要菜单上写的一直算数，后厨怎么做都可以调整。

Contract（约定）把 API 描述得足够精确，让两个人或两个团队各做一边，最后还能严丝合缝地对上。它通常写明：请求发到哪里、请求里有哪些字段、哪些必填、成功时返回什么、出错时返回什么。

一旦有别的东西依赖你的 API，比如你自己的手机应用、Zapier 这样的集成，或者合作方的系统，再改 API 就要付出实实在在的代价。所以约定文件被当作依据，以它为准，要先改约定，再改代码。AI 提出要改一个公开的约定时，问问它：谁在依赖它？他们会受到什么影响？

### 4. 认证和授权

这两个词听起来很像，经常被混在一起。

- 认证（authentication）回答“你是谁”。登录、会话、重置密码都属于它。工程师常简写成 authn。
- 授权（authorization）回答“你被允许做什么”。比如“只有团队负责人能删除工作区”，或者“免费用户每月只能看 10 条意见”。简写是 authz。

拿写字楼来说：前台查验你的证件，是认证；你的门禁卡能刷开哪几层楼、刷不开哪几层，是授权。

这两样都很容易在细节上出错，而一出错往往很严重：一个用户看到了另一个用户的数据，或者有人拿到了不该有的权限。所以，新增或修改登录和权限的决定，即使看起来是小改动，也需要你明确批准。已经批准的任务只覆盖它写明的内容，范围或风险一变，AI 就应该再问你。谈到权限时，用大白话一句句写清楚“谁可以对哪些数据做什么”，再问问 AI 打算怎么测试。

### 5. 范围明确的任务和纵向切片

范围明确的任务（bounded task）有一个清楚的结果、约定好的范围，以及能证明它做成了的检查。别人（一个人或另一个 AI）应该能把它当作一个合情合理的整体改动来审查。

技能会用一些数字来提醒检查难度。比如一个任务改动超过大约 5 个文件或 300 行代码，审查者就该看得更仔细些。这些都不是硬性上限。拆开能降低风险或者更方便检查时，才拆；拆开会让东西只做了一半、前后对不上时，相关的改动就放在一起。所有必要的检查照样都要跑，哪怕超过 3 条命令。

纵向切片（vertical slice）是产品里从上到下都能跑通的一小块：屏幕上一个小改动，加上它背后服务器的改动，再加上更底层数据库的改动，一起交付，从头到尾能用。可以想象从一块多层蛋糕上竖着切下薄薄一片，每一层都有。

第一个任务最好能让你看到或试到点什么。如果一个任务是用整个功能命名的（“做好登录功能”），或者目标很空泛（“优化代码”），就要多留个心眼。

### 6. 开发环境、预发布环境和生产环境

软件通常在三个地方运行：

- 开发环境（development）是你自己的电脑，或者 AI 的工作区。东西坏了也无所谓，没有真实用户。
- 预发布环境（staging）是一份跑在服务器上的副本，看起来和正式产品一样，但里面是测试数据。相当于正式演出前的彩排。
- 生产环境（production）就是正式的产品，有真实的用户、真实的数据，出了问题会有真实的后果。

有些小项目会跳过预发布环境，但道理不变：先在犯错成本低的地方试，再拿给真实用户。部署到生产环境需要明确的许可，因为那里出错会影响所有人。获准开发或测试某个改动，不等于获准上线。你会在 `ARCH.md` 和部署相关的文件里看到这几个名字。

### 7. 能反悔的决定和难反悔的决定

有些决定撤回来几乎没成本，有些则代价很大。

- 容易撤回的：换个字体、改个按钮名称、函数内部的代码怎么排。
- 很难撤回的：数据库的结构、公开 API 的网址、登录的方式、用哪家支付服务、用户注销账号后数据怎么处理、数据保存多久。

技能里有一份“需要批准”的清单，列的都是有风险或难以撤回的决定，AI 不能在这些方面自己拿主意。你批准了某个决定和对应的工作以后，AI 就不应该为同一件事反复问你。不过范围变了、风险变了，以及上线这类单独的权限，仍然要留意。

有个好习惯：每当 AI 要做一个选择，问问自己，“如果这个选错了，以后改起来有多痛？”答案是“很容易”，就让它继续；答案是“很痛”或者“得把用户数据迁走”，就停下来好好商量。

### 8. 测试和验证

测试（test）是一小段程序，用来检查另一段代码的表现是否符合预期。比如：“提交一条没有内容的意见，系统应该拒绝，并给出清楚的错误提示。”测试会自动运行，所以每次改动之后它都会再查一遍。

测试有两个用处。一是抓“回归”（regression），也就是原来好好的、后来不知不觉坏掉的地方。二是给“这个任务做完了吗”一个诚实的回答。

在 Standard 里，每个任务文件都有一节“验证”（verification），列出要运行的具体命令，以及每条命令应该得到什么结果。你不需要写测试，但不要在没有证据的情况下接受“做好了”。问问它跑了哪些命令、结果是什么。没检查到的部分，汇报里也应该写明。

### 9. 审查（review）

审查，就是在一个改动被正式收进项目之前，让第二个人或第二个 AI 读一遍。审查者会问：

- 这个改动做到任务要求的事了吗？
- 有没有把原来能用的东西弄坏？
- 有没有越过 `ARCH.md` 或 `RULES.md` 里定下的边界？
- 有没有在没批准的情况下，动了“需要批准”清单里的东西？

技能要求审查者把两件事分开判断：一是改动有没有做到要求的事，二是做得扎不扎实。测试全部通过，也可能掩盖“解决了错的问题”；解决了对的问题，代码也可能很脆弱。审查负责发现问题、核对证据，重要的决定和最后接不接受，仍然由你来定。

### 10. “说两遍就写下来”的习惯

这是技能想帮你养成的最有用的习惯，而且和技术无关：当你发现自己第二次解释同一件事时，就把它写进某个长期文件。

- 审查改动时说过两次的事：写进 `RULES.md`。
- 关于各部分怎么交换数据说过两次的事：写进 `docs/CONTRACTS/`。
- 关于产品应该怎样表现说过两次的事：写进 `docs/SPEC.md`。
- 对 AI 说过两次的事：写进 `AGENTS.md`。

任何需要你反复解释的事，下一个人、下一个 AI，或者三个月后的你，只要没人写下来，就不会知道。你可以直接说：“这件事我们已经讨论过两次了，请把它写进合适的项目文件。”

## 六、日常工作的节奏，以及可以复制的提示词

复制下面这些，把尖括号里的内容换成你的情况。

用 Standard 开始一个项目：

```text
我想做 <你的想法>。它是给 <谁> 用的，主要想解决 <问题>。
请用 constitution-skill 的 Standard 模式。只问会影响计划的问题，
需要我做决定的地方用简单的话解释，我拿不准时请给出默认建议。
把计划保存在项目里，并提出第一个小任务。先不要写应用代码。
```

弄懂计划：

```text
假设我是软件新手，带我过一遍这份计划：第一版会做什么，不做什么，
你做了哪些假设？哪些决定以后很难改？
```

做下一个任务：

```text
请做 docs/TASKS/ 里的下一个任务。先告诉我它会交付什么，再在任务范围内完成它，并运行它的验证。
如果需要新的重要决定或者更大的范围，先问我。
做完后告诉我：改了什么、检查了什么、结果如何，以及我可以怎么试用。
```

请第二个工具帮忙审查：

```text
请对照任务文件和项目文档，审查最近一次改动。
分开判断两件事：它有没有做到任务要求的事，以及做得扎不扎实。
按严重程度列出问题，核对验证证据。除非我要求，不要改代码。
```

记下一个决定：

```text
我们刚刚决定了 <决定>。请把它写进合适的项目文件。如果这个决定很难撤回，
请另外写一条决策记录，列出我们考虑过的方案，以及为什么选了这个。
```

在新对话里接着做：

```text
请先读 AGENTS.md 和当前的计划或任务，然后用几句话告诉我：
项目现在进展到哪里、下一步是什么、有哪些事在等我决定。
```

## 七、哪些事需要你批准

在下面这些方面做新的决定，或者修改已有的决定之前，AI 应该先得到你明确的同意：

- 其他软件会依赖的 API 的公开格式
- 数据库结构，或者会改变它的 migration
- 登录和权限
- 付款、计费、法律、隐私或合规相关的行为
- 删除数据，或者其他无法撤回的操作
- 正式产品怎么部署、部署在哪里

关于批准，有三点要知道：

- 你批准了一个任务，就覆盖了这个任务写明的内容。AI 不应该为同一个决定再问你一遍。
- 同意开发，不等于同意上线，也不等于同意删除真实数据。这些操作要按各自的权限来。
- 如果 AI 说某条规则让它停了下来，它应该指出是哪个文件、引用原文，并说明还缺哪个决定。如果它指不出来，可能是把自己的偏好当成了规则，你可以请它继续做下去。

## 八、常见的警示信号，以及可以怎么回应

| 发生了什么 | 你可以这样说 |
| --- | --- |
| AI 说“做好了”，但没说检查了什么 | “你运行了哪些命令？结果是什么？还有哪些没检查？” |
| 它加了你没要求的东西 | “请把 <某样东西> 去掉，它超出了这个任务的范围。” |
| 它想改数据库、登录或支付 | “请说明有哪些方案、你推荐哪个，以及每个方案以后改起来有多难。然后等我决定。” |
| 它问起一件你已经决定过的事 | “这件事我们在 <文件> 里已经决定了，请直接沿用。” |
| 它想上线，或者想删除真实数据 | “先不要。同意开发不包括这个。” |
| 出现一条你看不懂的错误信息 | “请用大白话解释这个错误：哪里坏了，为什么，你接下来打算怎么做。” |
| 计划里有你不认识的词 | “请用一个生活中的例子解释一下 <这个词>。”也可以去[新手词典](rookie-wiki_CN.md)里查。 |
| 一个任务越做越大 | “能不能先拆出一个更小、但从头到尾能跑通的第一步？” |
| 你要开一个新对话 | “请先读 AGENTS.md，再告诉我现在进展到哪里。” |
| 检查脚本报了 WARN | “请逐条解释这些警告，以及它们会不会影响这个任务。” |

## 九、用大白话说说检查脚本

技能里有一个检查脚本，用来看项目文档有没有缺少必须的部分。它会报告三种结果：`ERROR` 表示有地方要改；`WARN` 表示有地方值得看一眼，由你或 AI 决定怎么处理；`OK` 表示没有发现结构上的问题。你可以请 AI 运行它，再解释结果。

通过检查不能证明软件能用，因为脚本不会去运行任务里写的命令。在 Flash 模式下，它也判断不了任务约定写得好不好，所以总会多加一条提醒，请你另外检查任务本身。真正检查结果的那些办法，比如跑测试、核对来源、查看实际状态，仍然少不了。
