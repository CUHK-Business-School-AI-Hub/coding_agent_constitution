# 新手入門說明

[English](rookie-onboarding.md) · [简体中文](rookie-onboarding_CN.md)

這份說明寫給第一次用 AI 做軟件的人：剛啟動項目的產品經理、不寫程式的創業者、想把自己的經驗做成工具的設計師或分析師，或者只是好奇想試試的你。使用 constitution skill 不需要懂得寫程式。不過它寫出來的檔案裏會有一些工程上的詞，你也會被請來作幾個決定。這一頁講清楚三件事：工作大致怎樣推進，每個檔案有甚麼用，每一步可以對 AI 說甚麼。

建議先由頭到尾讀一遍，大約半小時，之後用到哪一節再回來翻。如果只是想查某個詞，可以看[新手詞典](rookie-wiki_HK.md)，裏面用淺白的說法解釋做應用程式時常見的詞。

如果只記一句話，就記這句：做甚麼、為甚麼做，由你決定；怎樣做，由 AI 提出方案並動手；決定過的事，記在項目檔案裏。

## 開始之前

你需要準備三樣東西：

- 一個 AI 編程工具：Codex、Cursor 或 Claude Code，有一個就足夠。
- 在這個工具裏裝好技能。[README 的「快速開始」](../../README_HK.md#快速開始)只要發一段話就能裝好。
- 一個項目資料夾，即是你電腦上專門存放這個項目的普通資料夾。空的也沒關係。

你不需要懂任何程式語言，不需要背熟這份說明裏的檔案名稱，也不需要自己挑選模板。這些交給 AI，它會告訴你它選了甚麼。

## 一、一個項目大致怎樣進行

### 用 Standard 處理新想法的第一個星期

假設你想做一個幫小團隊收集客戶意見的工具。用 Standard 的話，過程大致是這樣：

1. 你用平日說話的方式講出想法，包括還未想通的部分。
2. AI 問幾個會影響計劃的問題：給誰用、第一版必須做到甚麼、甚麼可以押後、甚麼絕對不能出錯。你已經答過的，它不會再問。
3. 你能回答的就回答。回答不了的，AI 會提出一個穩妥的預設選擇，並記為「假設」，日後可以再改。
4. AI 把計劃寫進項目裏的檔案。
5. 你把計劃讀一遍，哪裏不對就指出來。這一步最能省下日後的重做。
6. AI 提出第一個小任務，結果要清楚，也要有檢查方法。
7. 你說「開始」。AI 動手做，執行完檢查，再用淺白的說法告訴你改了甚麼、怎樣試用。
8. 如果你想，可以請第二個 AI 工具或者工程師審查一次改動。
9. 新的決定寫回檔案，然後進入下一個任務。

整個過程你都不用讀程式碼。你讀的是計劃、結果和簡短的匯報。

### 誰負責甚麼

通常有四個角色，一個人或一個工具可以身兼幾個。

你是負責人。目標、優先次序，以及那些改起來代價很大的事，都由你決定。有風險的改動要你批准，最後接不接受也由你作主。

實現者（implementer）是一個 AI 工具，在約定好的任務範圍內修改檔案、執行檢查。

審查者（reviewer）是另一個 AI 工具或一位工程師，對照任務和項目規則檢查改動。

項目檔案是大家共用的記憶。下一個對話、下一個工具或下一個人，都不用依賴某次舊對話裏講過的話。

Codex、Cursor 和 Claude Code 都可以做實現者，也都可以做審查者。按你手上的工具和實際工作安排，沒有固定分工。有一個習慣很有用：每次改動只安排一個主要修改者，以免兩個工具同時改同一個地方。

### 為甚麼要寫下來

AI 對一次對話的記憶很短，也帶不到新對話裏。寫進項目的檔案卻一直都在。計劃放在檔案裏，你就可以開新對話、換工具、休息一個星期，或者把項目交給別人，工作都能由寫下來的內容接着做，不用靠任何人的記性。

## 二、你的任務需要多少結構？

這個技能有幾種工作方式。你不需要叫出名稱，描述清楚任務，AI 會自己選。不過了解一下每種方式的樣子，心裏會更有底。

### 直接做：已經講清楚的小任務

任務很小、要求也清楚，AI 就應該直接做，再執行相應檢查。不用問答，也不建新檔案。

例子：改一個錯字；改一下按鈕上的文字；回答一個關於你程式碼的具體問題；把你貼進來的一份備忘錄縮短。

### Flash：輕量，適合各類工作

Flash 適合需要先理順、但用不着整套項目流程的任務。日常工作、資料搜集、寫文件、做軟件，以及做可以重複使用的能力（例如技能），都可以用它。

例子：比較三款收集意見的工具並推薦一款；做一個技能，把會議紀錄整理成同事都能重用的行動清單；寫一個小腳本，讀取用量匯出檔案，計算還剩多少額度；為採購團隊準備一份簡短的決策投影片；把一個團隊會議改到新時間，並通知參加的人。

### Standard：完整的軟件項目

Standard 適合要做出真正軟件的情況：它會持續發展，會有真實用戶，或者有幾個人、幾個 AI 工具一起參與。它會寫出整套項目文件，然後透過一個個經過檢查的小任務向前推進。

例子：給小團隊用的意見收集箱、公司內部的審批系統、預約服務、AI 客戶服務助手。

### Retrofit：已有程式碼，但沒有文件

如果你已經有一套沒有人寫過文件的程式碼，Retrofit（補建）會一部分一部分地補上文件，由你快要修改的那一塊開始。它不會一開始就想把所有東西寫清楚：當初的想法已經沒有人記得，由頭硬寫一份大文件，大部分內容只會是猜測。

### 拿不定主意？

問自己幾個問題：

- 要做甚麼、怎樣檢查，是不是已經很清楚？那就直接提出要求。
- 這是不是一件單獨的工作，例如一次比較、一份文件、一個腳本、一個技能或一個操作，只是需要先把目標和終點講定？那就用 Flash。
- 這是不是一個會持續做下去的產品，有用戶、有資料、有幾個組成部分？那就用 Standard。
- 是不是已經有很多程式碼？那就用 Retrofit。

真的無法判斷，就直接說：「我不確定這件事需要多少規劃。請推薦一種模式，用一兩句話說明原因。」由輕的開始也完全可以。等到事情多得難以掌握、幾個部分或幾個人要依賴穩定的約定，或者交接需要獨立的紀錄時，Flash 的工作可以再轉用更完整的結構。

## 三、Flash 一步一步來

### 任務約定

Flash 一開始，會先把任務講定，形成一份簡短的約定，文件裏叫 task contract。它包括七項內容。以下用一個例子貫穿：為產品團隊比較三種收集客戶意見的方法。

1. 目標：想要甚麼結果，為甚麼。「選出一種下個月就可以開始用的收集方法。」
2. 使用者或讀者：誰會用這個結果，或者由誰評判。「我們的產品團隊，大家都不是工程師。」
3. 背景：現在的情況，以及要參考的資料。「我上一季的筆記，還有我們已經試過的兩款工具。」
4. 範圍：包括甚麼，以及刻意不做甚麼。「比較三個方案。不要登記任何帳戶，也不要聯絡供應商。」
5. 限制：會影響結果的條件。「要在我們現有預算之內，也要能接駁我們正在用的通訊工具。」
6. 可觀察的完成標準：完成時會是甚麼樣子，怎樣檢查。「一頁紙的比較和建議，每個重要說法都註明來源。」
7. 未知項：未決定的問題和暫時的假設。「我們不知道其中一家現時的價錢，標示出來，不要猜測。」

小任務可能兩三句話就講完這七項。持續幾天，或者要交給別人接手的工作，就需要把它們寫下來。

### 結果不能隨便改，計劃可以調整

約定講的是「怎樣才算成功」。計劃講的是 AI 打算怎樣做到：用甚麼方法、分哪幾步、現在做到哪裏。某個方法行不通，或者有了更好的資料，計劃就應該調整。但結果不能跟着悄悄改變：AI 不應該降低標準、換掉讀者，或者為了遷就自己做出來的東西而改動交付內容。如果結果確實需要改，就要和你商量，並把改動寫下來。

還有一點：初稿、進度匯報，或者一個已經啟動的任務，都不等於完成。如果有東西仍在運行或者卡住了，AI 應該直接講清楚。

### 四種額外細節

在約定之外，AI 只補充任務真正需要的細節。一共有四種，一個任務可能用上幾種，也可能一種都不用。

行為，用在會重複運行的東西上：腳本、軟件功能、技能、智能體。值得寫清楚的是：輸入甚麼、怎樣啟動、輸出甚麼、兩次運行之間要保留甚麼、幾個例子（包括棘手的情況），以及輸入缺失或出錯時怎樣處理。以那個額度報告腳本為例，就是要問：匯出檔案是空的怎麼辦？額度那一項缺少了怎麼辦？

證據與判斷，用在資料搜集、比較、診斷和提出建議上。值得寫清楚的是：必須回答哪些問題、證據從哪裏來（要附日期，因為資訊會過時）、按甚麼標準比較各個選項、結論有多大把握。好的資料搜集會把「看到的事實」和「推論出來的判斷」分開。

內容與結構，用在文件、投影片、訊息這類給人看的東西上。值得寫清楚的是：寫給誰看、最想表達甚麼、大綱，以及呈現方式，即是格式、語氣和篇幅。像投影片這類講究版面的東西，檢查時要看實際呈現出來的效果，只看文字並不足夠。

行動，用在真的要改動某樣東西的時候：整理檔案、更改會議時間、更新一條紀錄、發送一份報告。值得寫清楚的是：具體改的是哪一個、現在是甚麼樣子、改完應該是甚麼樣子、事前必須符合甚麼條件、步驟次序，以及怎樣確認結果。操作發了出去，不代表已經成功。AI 應該查看實際結果，例如日曆上那個會議的新時間。

這些不用你來挑選。它們不是幾種不同的模式，也不需要各建一個檔案。例如一次市場比較最後要做成投影片，就同時用上證據和內容兩種；一個每星期出報告的智能體，可能四種都會用上。

### Flash 把東西放在哪裏

一次性的任務，在對話裏講清楚通常已經足夠。持續進行的工作，可以用一套很輕的結構：

- `AGENTS.md` 放穩定的項目背景：這是甚麼項目、重要檔案在哪裏、一直沿用的慣例，以及怎樣檢查工作。
- `docs/PLAN.md`（或者已有的任務說明）放任務約定、額外的細節、目前的計劃，以及已經檢查過甚麼的證據。

這只是一個起點，不是必須建立的檔案。如果一個技能已經在自己的 `SKILL.md` 寫清楚行為，或者項目裏已經有任務紀錄、資料格式定義，AI 應該直接引用，不要再複製一份。有需要的話，可以用 [AGENTS.md](../assets/flash-templates/AGENTS.md) 和 [PLAN.md](../assets/flash-templates/PLAN.md) 這兩個可選模板起步。

### 怎樣檢查 Flash 的結果

不同的結果，檢查方法也不一樣：

- 會運行的東西：用有代表性的例子實際試一試，看輸出。用假資料或演練（dry run）得出的結果，要註明是這樣得出的。
- 資料搜集：把重要的說法和來源、日期對一對，確認缺口和互相矛盾的地方都清楚列出。
- 文件或投影片：讀完成品；講究版面的，要看實際呈現的樣子。
- 操作：看操作之後的實際狀態，或者系統回傳的確認和狀態。

任何 Flash 任務完成時，都可以問這一句：「我們約定的內容裏，哪些完成了？你怎樣知道？還有甚麼未做完？」

### 可以直接複製的 Flash 提示詞

把尖括號裏的內容換掉：

```text
請用 constitution-skill 的 Flash 模式處理這個任務：<描述任務>。
結果是給 <誰> 用的。背景情況是：<筆記或檔案>。
先寫一份簡短的任務約定：目標、讀者、範圍和不做的事、限制條件、怎樣才算完成、未決定的問題。
只補充這個任務需要的細節，並把計劃和要達到的結果分開寫。
先在這個對話裏整理；如果建立項目檔案方便日後重用，才建立。
```

想了解更多，可以看 [Flash 指南](flash-mode.md)、[組件說明](flash-components.md)和[場景例子](flash-scenarios.md)（都是英文）。

## 四、Standard 一步一步來

### 規劃時的對話

Standard 由提問開始。問題通常圍繞這些方面：用戶是誰、要解決甚麼問題、第一版必須做到甚麼、甚麼可以押後、甚麼絕對不能出錯，以及預算、期限、私隱、必須配合的現有系統這類限制。問題沒有最低數量。AI 只應該問會影響計劃的問題，你已經講過的，它應該直接沿用。

幾個小建議：

- 「我不知道」是個好答案。AI 應該提出一個合理的預設選擇，用淺白的說法解釋，並標示為假設。
- 用你自己的說法講問題。「我們團隊的客戶意見散落在一個共用試算表裏，經常找不到」，比「我想要一個 React 應用程式」有用得多。
- 講講你想取代的是甚麼（一張試算表、一份問卷、一套人手流程），以及哪些東西你最不想失去。
- 如果問題裏有你不明白的詞，先問清楚那個詞再回答。也可以追問一句：「我答得不同，會改變甚麼？」

### 你會得到哪些檔案

Standard 會寫出一小套文件，一般放在 `docs/` 資料夾，另外在項目最外層放一個 `AGENTS.md`。每份檔案回答一個不同的問題。

`SPEC.md` 回答「這個產品能為用戶做甚麼」。裏面寫目標、用戶、主要流程、刻意不做的事（非目標）、限制條件，以及驗收標準，即是一條條可以檢查的「怎樣才算完成」。這裏不寫程式碼。

`ARCH.md` 回答「裏面有哪些部分，它們怎樣拼合起來」。裏面寫有哪些模組、各自負責甚麼、資料放在哪裏、選用了甚麼技術和原因，以及產品怎樣運行。它也會記下產品形態：這個項目屬於哪種常見的產品類型，加了哪些能力，用了哪套預設技術。

`RULES.md` 回答「每次改動都要守哪些規矩」。裏面是對這個項目真正有用的編碼慣例、測試要求和安全規則。泛泛的編程建議不放在這裏。

`CONTRACTS/` 回答「各部分之間究竟約定了甚麼」。裏面寫介面的格式、數據庫表的結構、事件訊息和檔案格式，寫得很精確，常常用標準格式，還會附上例子。

`DECISIONS/` 放那些很難反悔的決定，例如用哪種數據庫。每一條都會寫當時的背景、作了甚麼選擇、要付出甚麼代價，以及被否決的其他方案。工程師稱這類紀錄為 ADR（architecture decision record，架構決策紀錄）。

`TASKS/` 放接下來的一個個小任務。每個任務有一個目標、可以改和不可以改的範圍、驗收標準，以及用來檢查的具體命令。任務是一次性的：做完了、經驗也記下來了，就可以清理掉。

`AGENTS.md` 是給 AI 工具的說明書：先看哪裏、執行哪些命令、哪些地方很敏感、甚麼需要你批准，以及完成後怎樣匯報。

打個比喻：需求說明（SPEC）像樓盤的售樓書，架構（ARCH）像平面圖，規則（RULES）像建築規例，約定（CONTRACTS）像門框，所有要穿過的東西都要合尺寸。決策紀錄是簽了名的更改單，任務就是今日的工作單。

除了任務之外，這些檔案都要長期保留，項目有變化時要跟着更新。任務、草稿筆記和一次性的計劃，用完就可以丟棄。

### 看看樣例項目

技能附有一個填好的樣例，叫 [Feedback Inbox](../assets/examples/feedback-inbox/)。這是一個給 3 至 15 人小型產品團隊用的工具：從公開表格收集客戶意見，把意見歸納成主題，再把最有價值的那些變成開發任務。隨手翻翻，看看好的文件是甚麼樣子就可以，不用每一行都看懂。

有幾處值得留意：

- 它的需求說明列出了非目標，例如不取代團隊現有的任務追蹤工具，也不讓 AI 直接回覆客戶。把不做的事寫下來，AI 就不容易偏離方向。
- 它的驗收標準是任何人都能檢查的，例如「客戶可以透過公開表格提交意見，並看到確認頁面」。
- 它的第一條決策紀錄解釋了為甚麼把要發出的事件先存放在主數據庫，沒有另外加一個訊息服務：少維護一個服務，代價是多一點點延遲，能承受的流量也有上限。被否決的方案和原因都列了出來。
- 它的[第一個任務](../assets/examples/feedback-inbox/docs/TASKS/001-bootstrap-feedback-inbox.md)寫明了可以改哪些檔案、不可以改哪些檔案，以及用哪些命令證明它能用。

### 讀計劃時的檢查清單

技術選得好不好，你不用判斷。但你需要確認計劃和你的原意一致。可以逐條看一遍：

- 需求說明描述的用戶和問題，和你自己會怎樣講一致嗎？
- 非目標對不對？有沒有你絕不想在第一版出現、卻沒有列出的東西？或者列了進去，其實你需要？
- 每條驗收標準，你自己能檢查嗎？或者能看着別人檢查嗎？
- 這些假設你能接受嗎？
- 那些待定問題是否真的未有決定？有沒有甚麼事情依賴它們？
- 第一個任務完成後，你能看到或者試用到一些東西嗎？
- 遇到那些重大、難以反悔的選擇，AI 有沒有請你批准？有沒有用你聽得明白的話解釋各個選項？

只要有一條的答案是「不」或者「不確定」，就說出來。改計劃，比改軟件便宜得多。

## 五、檔案裏常見的十個概念

以下這十個概念會反覆出現。每一節都會講：它是甚麼，為甚麼和你有關，你可以做甚麼。

### 1. 假設和待定問題

假設，是寫下來的猜測，讓大家都知道這是猜的：「我們假設第一版每套系統只給一個團隊使用。」待定問題，是還未有人作決定的事：「匿名提交的意見，要不要附一條回覆連結？」

這兩樣都很正常。技能會把它們放在特別標示的段落，不會埋在正文裏。你要做的是讀一讀，確認或糾正這些假設，並留意有沒有任務依賴某個待定問題。依賴待定問題的任務，還不可以開工。

### 2. Schema 和 migration

Schema 是你的產品儲存資料的「形狀」。一張 `feedback` 表，有 `id`、`source`、`message`、`created_at` 這幾欄，就是一個 schema。它很像 Excel 試算表的標題列，分別在於數據庫會強制大家遵守。

Migration（遷移）是一段修改 schema 的腳本，改動會被記錄下來，也可以重複執行，例如「給 `feedback` 表加一欄 `tags`」。

有兩點值得知道。第一，一旦有了真實用戶，每次改 schema 都會碰到他們的資料：加一欄通常是安全的，改欄名、刪除欄位，或者改變某一欄的含義，往往有風險。第二，大多數團隊把 migration 視為只能向前走的：發現某個 migration 有錯，就再寫一個新的去修正，不會回頭改舊的。

所以，新增或修改 schema 的決定需要你明確批准。如果已批准的任務裏寫清楚了這項改動，AI 可以照着做，不必再問一次。在正式運行的產品上執行 migration，還需要另外的權限。你永遠不用自己寫 migration，但要留意它甚麼時候正在發生，並問一句：「這個可以還原嗎？現有的資料會怎樣？」

### 3. API 和 contract

API（application programming interface，應用程式介面）是一個軟件和另一個軟件溝通的方式。最常見的是 web API：一個程式向某個網址發出請求（request），另一個程式回傳一個回應（response），內容通常是一種叫 JSON 的文字格式。可以把它想像成餐廳的餐牌：上面寫着可以點甚麼、會上甚麼菜；只要餐牌上寫的一直算數，廚房怎樣煮都可以調整。

Contract（約定）把 API 描述得足夠精確，讓兩個人或兩個團隊各做一邊，最後仍然完全吻合。它通常寫明：請求發到哪裏、請求裏有哪些欄位、哪些必須填寫、成功時回傳甚麼、出錯時回傳甚麼。

一旦有其他東西依賴你的 API，例如你自己的手機 app、Zapier 這類整合，或者合作夥伴的系統，再改 API 就要付出實實在在的代價。所以約定檔案被視為準則，一切以它為準，要先改約定，再改程式碼。AI 提出要改一個公開的約定時，問問它：誰在依賴它？他們會受到甚麼影響？

### 4. 認證和授權

這兩個詞聽起來很像，經常被混為一談。

- 認證（authentication）回答「你是誰」。登入、保持登入狀態（session）、重設密碼都屬於它。工程師常簡寫為 authn。
- 授權（authorization）回答「你獲准做甚麼」。例如「只有團隊負責人可以刪除工作區」，或者「免費用戶每月只能看 10 條意見」。簡寫是 authz。

以寫字樓為例：大堂保安查看你的證件，是認證；你的門禁卡可以開哪幾層、開不到哪幾層，是授權。

這兩樣都很容易在細節上出錯，而一出錯往往很嚴重：一個用戶看到另一個用戶的資料，或者有人取得了不應有的權限。所以，新增或修改登入和權限的決定，即使看起來只是小改動，也需要你明確批准。已批准的任務只涵蓋它寫明的內容，範圍或風險一有改變，AI 就應該再問你。談到權限時，用淺白的話一句句寫清楚「誰可以對哪些資料做甚麼」，再問問 AI 打算怎樣測試。

### 5. 範圍明確的任務和縱向切片

範圍明確的任務（bounded task）有一個清楚的結果、約定好的範圍，以及能證明它做成了的檢查。其他人（一個人或另一個 AI）應該能把它當作一個合理的整體改動來審查。

技能會用一些數字提醒檢查難度。例如一個任務改動超過大約 5 個檔案或 300 行程式碼，審查者就應該看得仔細些。這些都不是硬性上限。拆開能降低風險或者更方便檢查時，才拆；拆開會令東西只做了一半、前後對不上時，相關改動就放在一起。所有必要的檢查照樣都要執行，即使超過 3 條命令。

縱向切片（vertical slice）是產品裏由上到下都能運作的一小塊：畫面上一個小改動，加上它背後伺服器的改動，再加上更底層數據庫的改動，一併交付，由頭到尾能用。可以想像從一件千層蛋糕上直切下薄薄一片，每一層都有。

第一個任務最好能讓你看到或試到一些東西。如果一個任務用整個功能命名（「做好登入功能」），或者目標很空泛（「優化程式碼」），就要多加留意。

### 6. 開發環境、預發佈環境和正式環境

軟件通常在三個地方運行：

- 開發環境（development）是你自己的電腦，或者 AI 的工作區。東西壞了也無所謂，沒有真實用戶。
- 預發佈環境（staging）是一份在伺服器上運行的副本，看起來和正式產品一樣，但裏面是測試資料。相當於正式演出前的綵排。
- 正式環境（production）就是正式的產品，有真實的用戶、真實的資料，出了問題會有真實的後果。

有些小項目會略過預發佈環境，但道理不變：先在犯錯成本低的地方試，再交給真實用戶。部署到正式環境需要明確許可，因為那裏出錯會影響所有人。獲准開發或測試某項改動，不等於獲准上線。你會在 `ARCH.md` 和部署相關的檔案裏見到這幾個名稱。

### 7. 可以反悔和難以反悔的決定

有些決定還原起來幾乎沒有成本，有些則代價很大。

- 容易還原的：換個字型、改個按鈕名稱、函數內部的程式碼怎樣排列。
- 很難還原的：數據庫的結構、公開 API 的網址、登入的方式、用哪家付款服務、用戶刪除帳戶後資料怎樣處理、資料保存多久。

技能裏有一份「需要批准」的清單，列出的都是有風險或難以還原的決定，AI 不可以在這些方面自作主張。你批准了某個決定和相應的工作之後，AI 就不應該為同一件事反覆問你。不過範圍變了、風險變了，以及上線這類獨立的權限，仍然要留意。

有個好習慣：每當 AI 要作一個選擇，問問自己：「如果這個選錯了，日後改起來有多痛？」答案是「很容易」，就讓它繼續；答案是「很痛」或者「要把用戶資料搬走」，就停下來好好商量。

### 8. 測試和驗證

測試（test）是一小段程式，用來檢查另一段程式碼的表現是否符合預期。例如：「提交一條沒有內容的意見，系統應該拒絕，並給出清楚的錯誤提示。」測試會自動執行，所以每次改動之後它都會再查一次。

測試有兩個用處。一是找出「回歸」（regression），即是原本運作正常、後來不知不覺壞掉的地方。二是為「這個任務做完了嗎」給出一個誠實的答案。

在 Standard 裏，每個任務檔案都有一節「驗證」（verification），列出要執行的具體命令，以及每條命令應得出甚麼結果。你不需要寫測試，但不要在沒有證據的情況下接受「做好了」。問問它執行了哪些命令、結果是甚麼。沒有檢查到的部分，匯報裏也應該寫明。

### 9. 審查（review）

審查，就是在一個改動正式收進項目之前，讓第二個人或第二個 AI 讀一遍。審查者會問：

- 這個改動做到任務要求的事嗎？
- 有沒有把原本能用的東西弄壞？
- 有沒有越過 `ARCH.md` 或 `RULES.md` 定下的界線？
- 有沒有在未獲批准的情況下，動了「需要批准」清單上的東西？

技能要求審查者把兩件事分開判斷：一是改動有沒有做到要求的事，二是做得穩不穩妥。測試全部通過，也可能掩蓋「解決了錯的問題」；解決了對的問題，程式碼也可能很脆弱。審查負責找出問題、核對證據，重要的決定和最後接不接受，仍然由你決定。

### 10. 「講兩次就寫下來」的習慣

這是技能想幫你養成的最有用的習慣，而且和技術無關：當你發現自己第二次解釋同一件事，就把它寫進某個長期檔案。

- 審查改動時講過兩次的事：寫進 `RULES.md`。
- 關於各部分怎樣交換資料講過兩次的事：寫進 `docs/CONTRACTS/`。
- 關於產品應該怎樣表現講過兩次的事：寫進 `docs/SPEC.md`。
- 對 AI 講過兩次的事：寫進 `AGENTS.md`。

任何需要你反覆解釋的事，下一個人、下一個 AI，或者三個月後的你，只要沒有人寫下來，就不會知道。你可以直接說：「這件事我們已經討論過兩次，請把它寫進合適的項目檔案。」

## 六、日常工作的節奏，以及可以複製的提示詞

複製以下內容，把尖括號裏的部分換成你的情況。

用 Standard 開始一個項目：

```text
我想做 <你的想法>。它是給 <誰> 用的，主要想解決 <問題>。
請用 constitution-skill 的 Standard 模式。只問會影響計劃的問題，
需要我作決定的地方用淺白文字解釋，我拿不定主意時請給出預設建議。
把計劃儲存在項目裏，並提出第一個小任務。先不要寫應用程式碼。
```

弄明白計劃：

```text
假設我是軟件新手，帶我看一遍這份計劃：第一版會做甚麼，不做甚麼，
你作了哪些假設？哪些決定日後很難改？
```

做下一個任務：

```text
請做 docs/TASKS/ 裏的下一個任務。先告訴我它會交付甚麼，再在任務範圍內完成它，並執行它的驗證。
如果需要新的重要決定或者更大的範圍，先問我。
完成後告訴我：改了甚麼、檢查了甚麼、結果如何，以及我可以怎樣試用。
```

請第二個工具幫忙審查：

```text
請對照任務檔案和項目文件，審查最近一次改動。
分開判斷兩件事：它有沒有做到任務要求的事，以及做得穩不穩妥。
按嚴重程度列出問題，核對驗證證據。除非我要求，不要修改程式碼。
```

記下一個決定：

```text
我們剛剛決定了 <決定>。請把它寫進合適的項目檔案。如果這個決定很難還原，
請另外寫一條決策紀錄，列出我們考慮過的方案，以及為甚麼選了這個。
```

在新對話裏繼續：

```text
請先讀 AGENTS.md 和目前的計劃或任務，然後用幾句話告訴我：
項目現在進展到哪裏、下一步是甚麼、有哪些事在等我決定。
```

## 七、哪些事需要你批准

在以下這些方面作新的決定，或者修改已有的決定之前，AI 應該先取得你明確的同意：

- 其他軟件會依賴的 API 的公開格式
- 數據庫結構，或者會改變它的 migration
- 登入和權限
- 付款、收費、法律、私隱或合規相關的行為
- 刪除資料，或者其他無法還原的操作
- 正式產品怎樣部署、部署在哪裏

關於批准，有三點要知道：

- 你批准了一個任務，就涵蓋了這個任務寫明的內容。AI 不應該為同一個決定再問你一次。
- 同意開發，不等於同意上線，也不等於同意刪除真實資料。這些操作要按各自的權限處理。
- 如果 AI 說某條規則令它停了下來，它應該指出是哪個檔案、引用原文，並說明還欠哪個決定。如果它指不出來，可能是把自己的偏好當成了規則，你可以請它繼續做下去。

## 八、常見的警號，以及可以怎樣回應

| 發生了甚麼 | 你可以這樣說 |
| --- | --- |
| AI 說「做好了」，但沒說檢查了甚麼 | 「你執行了哪些命令？結果是甚麼？還有哪些未檢查？」 |
| 它加了你沒有要求的東西 | 「請把 <某樣東西> 刪除，它超出了這個任務的範圍。」 |
| 它想改數據庫、登入或付款 | 「請說明有哪些方案、你推薦哪一個，以及每個方案日後改起來有多難。然後等我決定。」 |
| 它問起一件你已經決定了的事 | 「這件事我們在 <檔案> 裏已經決定了，請直接沿用。」 |
| 它想上線，或者想刪除真實資料 | 「暫時不要。同意開發不包括這個。」 |
| 出現一條你看不明白的錯誤訊息 | 「請用淺白的說法解釋這個錯誤：哪裏壞了，為甚麼，你下一步打算怎樣做。」 |
| 計劃裏有你不認識的詞 | 「請用一個日常生活的例子解釋一下 <這個詞>。」也可以在[新手詞典](rookie-wiki_HK.md)裏查。 |
| 一個任務越做越大 | 「可不可以先拆出一個較小、但由頭到尾都能運作的第一步？」 |
| 你要開一個新對話 | 「請先讀 AGENTS.md，再告訴我現在進展到哪裏。」 |
| 檢查腳本報了 WARN | 「請逐條解釋這些警告，以及它們會不會影響這個任務。」 |

## 九、用淺白的說法講講檢查腳本

技能裏有一個檢查腳本，用來看項目文件有沒有欠缺必須的部分。它會報告三種結果：`ERROR` 表示有地方要修正；`WARN` 表示有地方值得留意，由你或 AI 決定怎樣處理；`OK` 表示沒有發現結構上的問題。你可以請 AI 執行它，再解釋結果。

通過檢查不能證明軟件能用，因為腳本不會執行任務裏寫的命令。在 Flash 模式下，它也無法判斷任務約定寫得好不好，所以總會多加一條提醒，請你另外檢查任務本身。真正檢查結果的方法，例如執行測試、核對來源、查看實際狀態，仍然不可缺少。
